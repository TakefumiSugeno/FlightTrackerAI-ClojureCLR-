## 1. 【スクレイピング・アーキテクト】レビュー指摘と対応方針

### 指摘 1.1: 永続プロファイルディレクトリの `SingletonLock` 残留による次回起動時クラッシュ・デッドロック
- **重要度**: **Critical**
- **指摘内容**:
  Playwright の `LaunchPersistentContextAsync(profileDir, options)` は Chromium プロファイルディレクトリ内に `SingletonLock` を生成する。クラッシュや強制終了時にロックが残留すると、次回起動時に「別のプロセスが使用中」と判定され起動失敗やフリーズが生じる。プロセス内排他ロック `scraper-lock` ではクラッシュ後のロック残留に対処できない。
- **対応方針**:
  - `create-context-async` 実行直前に、ロック保持中の Chromium プロセスが存在しないことを確認した上で、古い `SingletonLock` / `SingletonCookie` / `SingletonSocket` を安全にクリーンアップするフォールバックロジックを実装。
  - プロセス終了時フック (`AppDomain.CurrentDomain.ProcessExit`) に `close-context-async` を登録。

### 指摘 1.2: ClojureCLR における同期ブロッキング呼び出しと Bot 検知ポーリングのスタック消費
- **重要度**: **Critical**
- **指摘内容**:
  ClojureCLR には `async/await` がなく `await-task` で同期ブロックしている。F# 版の再帰関数 `pollForCards` を素朴に関数再帰で移植するとスタック消費による `StackOverflowException` の危険がある。また、Skyscanner の Bot 長押し（5.5秒）＋ 有頭手動待機（最大60秒）中にワーカースレッドが完全拘束される。
- **対応方針**:
  - `poll-for-cards` は自己再帰ではなく Clojure の **`loop [attempts remaining ...]` / `recur`** で実装し、スタック消費を完全にゼロにする。
  - ポーリングの各ループで巡回停止フラグ（`worker-running` / `cancellationToken`）を評価し、待機中であっても即座にループを脱出・リソース解放できるようにする。

### 指摘 1.3: `ensure-playwright-browsers-installed!` の多重実行・失敗時再試行・例外制御
- **重要度**: **Major**
- **指摘内容**:
  `Microsoft.Playwright.Program/Main` 呼び出し時の引数型変換 (`String[]`) と多重実行防止、ダウンロード失敗時の再試行制御が必要。
- **対応方針**:
  - `atom` で状態（`:uninstalled`, `:installing`, `:installed`, `:failed`）を管理し、多重実行を完全に防止。
  - 成功・失敗時のログ出力を明示し、失敗時はクールダウンを設けて無駄なダウンロード試行を抑止。

### 指摘 1.4: PerimeterX (PRESS & HOLD) 自動解除の iframe / Shadow DOM / マウス軌跡対応
- **重要度**: **Major**
- **指摘内容**:
  ボタン中心へ瞬時にワープ移動すると Bot と判定されて解除されない。また、キャプチャ要素が iframe / Shadow DOM に配置されるケースがある。
- **対応方針**:
  - マウス移動に複数ステップ（自然な軌跡）をエミュレート。
  - セレクタ探索のフォールバック強化。
  - 自動長押し失敗時は有頭モード時にわかりやすい手動解除ガイダンスを出力し最大60秒待機。

### 指摘 1.5: Stealth 注入スクリプトと Playwright 1.62 Chromium バージョンの整合
- **重要度**: **Major**
- **指摘内容**:
  UserAgent / Sec-Ch-Ua のハードコード値（Chrome 133）と Playwright 1.62 の Chromium バージョンの乖離による検知リスク。
- **対応方針**:
  - Playwright 1.62 のデフォルトと整合させたヘッダー設定および Stealth 初期化スクリプト (`AddInitScriptAsync`) の徹底。

### 指摘 1.6: 例外発生時の完全なリソース解放チェーン
- **重要度**: **Minor**
- **指摘内容**:
  `page` ➔ `context` ➔ `playwright` の多重ネスト解放において、一部で例外が発生しても他がリークしないよう保護する必要がある。
- **対応方針**:
  - 各解放ステップを個別の `try-catch` で保護し、ゾンビプロセス・メモリリークを確実に防止。

## 2. 【QA / テストエンジニア】レビュー指摘と対応方針

### 指摘 2.1: 実ブラウザ依存コードのテスト分離戦略とオフライン/CI環境での決定論的テスト
- **重要度**: **Critical**
- **指摘内容**:
  単体テスト実行時（`./scripts/test.ps1`）に本物の実ブラウザを起動したり外部サイトへ通信すると、オフライン環境での失敗、テスト実行時間増大、IPブロックなどの問題が発生する。
- **対応方針**:
  - **ブラウザ通信層と抽出・パース層の分離**:
    - `parse-offer-element` や純粋ロジックは単体テストで完全検証。
    - 実ブラウザを使用した End-to-End テストはオプトインフラグ（環境変数等）でのみ実行する統合テストとして分離。
  - 標準の `./scripts/test.ps1` は実ブラウザを起動せず数秒で決定論的に全テストが通過する設計を維持。

### 指摘 2.2: 実ブラウザ実装に伴うテストカバレッジ急落（80%未達）リスク
- **重要度**: **Critical**
- **指摘内容**:
  `scrape-async` 内に大量のブラウザ操作コードを追加すると、実ブラウザテストを行わない限りカバレッジが 30%〜40% に急落する。
- **対応方針**:
  - Skyscanner の Bot検知判定を純粋関数 `detect-bot-challenge [title content px-element-found?]` として切り出し、単体テストで境界値（タイトル・本文・要素有無の全パターン）を網羅。
  - カードDOM要素からの抽出マッピングをテスト可能なヘルパー関数として構造化し、単体テストで網羅的にテストしてカバレッジ 80% 以上を確実に達成する。

### 指摘 2.3: `./scripts/test.ps1` におけるブラウザ未導入環境フェイルセーフ
- **重要度**: **Major**
- **指摘内容**:
  ブラウザ未導入環境でテストスクリプトが自動ダウンロードでブロックされないようにする。
- **対応方針**:
  - 単体テストではブラウザプロビジョニングをモック/バイパスできるように設計。

### 指摘 2.4: スクレイピング境界値・異常系のテスト網羅
- **重要度**: **Major**
- **指摘内容**:
  満席表記、複数通貨記号、航空会社名欠損（`img[alt]`）、乗継数表記揺れのテストケースが不足している。
- **対応方針**:
  - テーブル駆動テストにより、各種表記揺れ・異常系の網羅テストを追加。

### 指摘 2.5: テスト実行時の環境汚染防止
- **重要度**: **Minor**
- **指摘内容**:
  テスト実行で `doc/work/` 配下に不要なファイルが残留する懸念。
- **対応方針**:
  - テスト用テンポラリディレクトリの使用およびクリーンアップ。
